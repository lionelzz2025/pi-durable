## 测试原则

- 自动化用 Node 内置 test runner + assert（若无不可替代需求不引入测试框架）。
- store/API 不调用模型；桥接用捕获注册工具的测试宿主与真实 HTTP 服务，另做官方 pi 加载检查。
- 每组生成唯一 data/test-runs/<run-id>/；不用正式 data/assistant/；不直接删除文件。
- 端口由测试随机分配，进程用 spawn 无 shell，明确 deadline；finally 中只终止本测试创建的子进程。
- 断言返回数据及重开后的状态，不能用日志出现“成功”代替验证。
- 脚本实际落地为 `npm test`（= `node --test "tests/**/*.test.ts"`）与 `npm run typecheck`；新增源码、扩展和测试均纳入类型检查。
  （计划里写的 `npm run test:assistant` 未采用：一个仓只一套测试，没必要分名。）
- 没有真实网络/模型/微信条件不得伪造端到端结论。

- 用户本机设置 token，启动服务；专用 pi 进程用 -e 显式加载桥接扩展。
- 用户确认现有微信连接归属；不终止未知 pi，不删除锁，不占用其他会话连接。
- 检查插件发送者授权逻辑，记录安装版本和实际宿主模式；用户本人完成 /wechat login 与 /wechat start。
- 使用唯一测试前缀（例如 assistant-acceptance-<timestamp>），不操作真实待办。
- 插件操作命令以实施时实际版本为准，不能盲用计划里的示例。

## 故障处理和停止条件

- API不可用、存储无法独占、事务原子性失败：停在对应phase，不转为内存存储或绕过锁。
- 官方扩展类型/宿主加载不兼容：先记录最小复现，再提版本或适配建议，不更改全局pi安装。
- 微信主动发送/登录受限：不改第三方源码或冒用另一接收者；首版被动闭环按实际条件验收。
- 回归修复后按项目要求做 post-fix-prevention-review，再声称问题已解决。
